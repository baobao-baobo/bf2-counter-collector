## 1. 我们要解决什么问题

### 1.1 场景

BlueField-2 是一块智能网卡——一台专做网络数据处理的小型计算机。数据请求（数据包、内存读写请求等）进入网卡后，要依次穿过一串硬件组件才能离开，就像快递包裹进入分拣中心后要依次经过入口分拣台、内部传送带、缓存货架、仓库门口、出口装车台。BF2 里的这些"站台"有名字：HNF（入口分拣台）、tilenet/SkyMesh（内部传送网）、L3（缓存货架）、MSS（内存仓库的门口）、eSwitch（出口装车台）。

不同种类的业务走不同的固定路线——从哪个门进、经过哪些站台、从哪个门出。每条这样的固定路线，我们称为一条**数据路径**。例如：Arm 核访问内存走 CR 类路径；网络流量进入 Arm 走 NAD 类路径；网络流量转发到主机/出口走 NHD 类路径。目前梳理出 8 条路径（P1–P8），论文中归为六类（CR/IH/IB/NAD/NHD/WB）。

每个站台上装有仪表——硬件计数器。整块网卡约有 143 条可读计数器（论文工作选用其中约 52 条），采集系统每秒读一次，记录"这一秒里某某事件发生了多少次"。

### 1.2 目标

给定一个正在跑真实负载的系统，回答一个问题：

> **当前负载下，哪一条数据路径是最繁忙的？**

"最繁忙"的严格含义是：**最接近自身容量极限的那一条**（排队论的叫法是"饱和"）。模型每个采集周期（1 秒）输出每条路径一个数，排序取最大，就是答案。

### 1.3 为什么值得做

定位繁忙路径是性能分析的第一步：先知道堵在哪条路上，才谈得上分析为什么堵、怎么优化。而网卡内数据路径长、组件多、业务混合，靠肉眼翻计数器读数是看不出"哪条路最忙"的——这正是需要一个判定模型的原因。

## 2. 难在哪里：三条直觉路线为什么都走不通

### 2.1 路线一：直接看队长

"哪条路忙，看哪个站台堆的包裹最多不就完了？"——排队长度确实是刻画拥堵最直观的量，学术前沿的 PathFinder 系统正是这样定位瓶颈的。**但我们的计数器清单里，没有一条直接报告排队长度或等待时间的计数器。** 想"看队长"，没有仪器。这是硬件事实，也是整个设计最根本的约束。

### 2.2 路线二：用公式推算队长

排队论有一条基石定律（Little's Law，李特尔定律）：一支队伍的平均长度 = 到达速率 × 平均等待时间。到达速率我们的计数器能测；**等待时间却没有计数器**。有人尝试用"事先标定的常数等待时间"代进公式——2026-09-17 的修订分析表明：常数乘上速率，得到的其实不是队长，而是利用率（忙不忙的比例），等待的成分整个丢掉了。这条路不是数据质量问题，是理论上就走不通。

### 2.3 路线三：看哪条路径流量最大

流量大不等于忙。一条小路走 100 件包裹可能已经爆仓，高速公路走 500 件还空空荡荡——**不同路径容量不同**，流量绝对值不可比。而且只挑路径入口处的一个计数器代表整条路径，可信度不足（这版方案在设计中已被纠正，教训保留在此）。

### 2.4 小结

直接量队长：没有仪器；公式推算：缺等待时间，理论上不成立；单点流量比较：口径不公平。三条直觉路线全部受阻。于是有了本模型的核心转译——下一章。

## 3. 我们的答案：把"量队长"换成"比压力"

### 3.1 关键转译

仔细想会发现：我们要的答案**并不需要知道队伍有多长**。只需要知道：**每条路径离"撑爆"还有多远**。前者需要绝对值（队长），后者只需要相对位置（压力百分比）。

比喻：不必知道每支队伍具体排了几个人，只要知道每支队伍"排到门口的进度百分比"——A 队排到门口 80% 处，B 队排到 30% 处，谁更紧张一目了然。两队相差 50 个百分点，这就是排序依据。

### 3.2 模型做的事（一句话）

给网卡里每一个计数器配一把"0–1 压力刻度尺"——读数接近 0 表示它盯的那一环几乎空闲，接近 1 表示那一环接近饱和；然后沿每条路径，把这些压力值汇总成一个**路径压力指数**；指数最大的路径就是最繁忙路径。

### 3.3 借鉴了谁（各一句话）

- **PathFinder**（SIGCOMM'25）：逐组件算占用、沿路径求和、取最大者定为瓶颈。我们借用其"累加排序"的哲学与"占用账本"的功能定位；放弃其依赖等待时间的"时间账本"（原因见 2.2）。
- **操作分析**（Denning–Buzen 1978 / Lazowska 1984）：利用率 = 速率 × 平均服务时间；容量 = 平均服务时间的倒数。为"速率除以容量"这类归一化提供理论依据。
- **USE 方法**（Brendan Gregg）：检查三样东西——利用（Utilization）、饱和（Saturation）、错误（Errors）。我们的证据分级与之同源。
- **DCTCP / DCQCN**（数据中心拥塞控制）：交换机把"缓冲深度越过阈值的包"打上标记，作为拥塞信号。BF2 的 AF 类计数器就是这一思想的硬件版。
- **MPKI + min-max 缩放**（性能分析常用手段）：把异质指标缩放进统一区间。
- **NVIDIA DCGM**：以"引擎利用率百分比"呈现 GPU 内部各引擎负载——与本模型"逐组件压力百分比"的呈现方式同型。

### 3.4 范围裁定：本模型明确不做什么

背压/瓶颈类计数器只能覆盖约半数转发点（L3、PCIe、核内都有缺口），延迟类计数器整体缺失。因此本模型**只做路径级繁忙度判定**（对应 PathFinder 的 PFAnalyzer 角色）；顶点级定位、一切延迟类方法，留作未来工作。这是与用户讨论后于 2026-09-17 明确的裁定，手册与技术文档均按此口径。

## 4. 模型总览：三层索引机制

### 4.1 一句话版

全量计数器 → 归一化成 0–1 压力值 → 每个组件取最大 → 沿路径求和 → 取最大的路径。

### 4.2 结构图

```
数据请求 ──► [HNF] ──► [tilenet/SkyMesh] ──► [L3] ──► [MSS] ──► ... ──► [eSwitch] ──► 出口
                │           │               │        │
                └── 每个组件挂 1~N 个计数器，每秒读一次增量

第 1 层（每个计数器）    n_c = 归一化(读数)        ∈ [0,1]     "这一环离饱和还有多远"
第 2 层（每个组件）      v_j = max(n_c)           ∈ [0,1]     "组件最紧的环节有多紧"
第 3 层（每条路径）      L_p = Σ v_j               ≥ 0        "路径总压力有多大"

判定：L_p 最大的路径 = 当前最繁忙路径
```

### 4.3 三层各自回答的问题

| 层     | 输入          | 输出               | 回答的问题         |
| ----- | ----------- | ---------------- | ------------- |
| 第 1 层 | 一个计数器的一秒读数  | 压力指数 n_c ∈ [0,1] | 这一环离饱和还有多远？   |
| 第 2 层 | 一个组件上全部 n_c | 组件压力 v_j（含伴随量）   | 这个组件最紧的环节有多紧？ |
| 第 3 层 | 一条路径上全部 v_j | 路径压力 L_p（含伴随量）   | 这条路径的总压力有多大？  |

### 4.4 为什么是"先取最大、后求和"

先记结论，第 6 章给完整论证：同一个组件上的多个计数器，大多是**同一支队伍**上的多台仪表，所以取最大（同一支队伍只看最严峻的一台表）；不同组件是**不同队伍**，所以求和。max 与 Σ 的分界，就是"同一队列"与"不同队列"的分界。

### 4.5 全流程一瞥（示意数字，仅演示流程）

假设 CR 路径经过四个组件，某负载下的压力值为：

| 组件       | HNF | tilenet | L3  | MSS |
| -------- | --- | ------- | --- | --- |
| 组件压力 v_j | 0.6 | 0.4     | 0.7 | 0.3 |

则 CR 路径的压力指数 L_CR = 0.6 + 0.4 + 0.7 + 0.3 = **2.0**。同一时刻另一条路径 L_NAD = 0.8。判定：CR 路径更繁忙。全流程就是这样——下面三章解释每一个数是怎么算出来的、为什么这样算是合理的。

## 5. 第一层详解：给每块仪表配一把尺

### 5.1 归一化的动机：统一汇率

各计数器的单位五花八门："次/秒"（访问次数）、"字节/秒"（流量）、"周期数"（缓冲状态）、"命中次数"（缓存）。**单位不同，就不能相加比较**——身高、体重、心率不能直接求和评健康，得先换算成同一尺度。

第一层做的事就是统一汇率：把每个读数都换算成**同一个问题**的答案——"这一环离饱和还有多远"——答案统一用 0–1 表示。0 = 空闲，1 = 饱和。此后所有数都在回答同一个问题，才可以进入第 2、3 层的融合与求和。**这是第一层存在的全部理由。**

### 5.2 尺子的通用构造法：两个锚点

给一块仪表配"0–1 压力刻度尺"，本质是找两个参照点（锚点）：

- **空闲锚点 λ_idle**：系统空闲时这块仪表的背景读数——背景噪声、心跳流量，就像收银台没客人时打印机的咔嗒声。我们已有实测基线（G 系列实验的空闲采样）。
- **饱和锚点 λ_sat**：把它盯的那一环打到饱和时的读数——通过一次应力标定获得（例如用 membench 打满内存，记下内存相关计数器的平台值）。

有了两个锚点，任何当前读数 λ 都能换算成"在空闲→饱和这条刻度上走到了百分之几"。类比：体温计出厂时标定了 35°C 和 42°C 两个刻度，之后任何读数都在这个刻度上定位。

### 5.3 五类仪表、六种公式

计数器按"它测的是什么"分成五类，对应六种归一化公式。

#### 5.3.1 频率类——跨度归一化（主力公式）

频率类仪表数"每秒发生了多少次某事件"（访问数、读写数、拍数）。

```
n = clamp( (λ − λ_idle) / (λ_sat − λ_idle), 0, 1 )
```

- **λ**：当前窗口的实测速率。
- **λ_idle**：空闲背景读数（减去它，空闲时 n 才等于 0）。
- **λ_sat**：饱和读数（应力标定得到）。
- **clamp**：把结果裁剪进 [0,1]。突发时 λ 可能略超 λ_sat，封顶为 1；空闲波动时 λ 可能略低于 λ_idle，保底为 0。没有这个裁剪，[0,1] 的契约就破了，后面的求和就失去可比性。

**为什么合理**（排队论视角）：一个环节饱和时，它的到达率恰好等于服务率（来多少就能处理多少，处理速度已到顶）。所以 λ_sat 就是服务率，n = λ/λ_sat ≈ 利用率——"跨度归一化就是用实验标定出来的利用率"。

**实例**（真实数据）：HNF 的 A72_ACCESS 计数器，空闲基线 0.7M 次/秒，饱和参考 195.7M 次/秒（stress-ng --cache 实测），xz 负载下读得 67.1M 次/秒：

```
n = (67.1 − 0.7) / (195.7 − 0.7) ≈ 0.34
```

含义：xz 把 HNF 的核请求面推到了"距饱和 34%"的位置。

#### 5.3.2 频率类——容量归一化（替代公式）

当仪表的单位是字节、且所盯资源的容量 C 已知或好测时，直接用容量做锚点：

```
n = λ / C
```

这就是最经典的利用率 ρ = λ/C。操作分析（Denning–Buzen 利用率律）保证它合法：**容量 = 平均服务时间的倒数**，所以 λ/C = λ × 平均服务时间 = 利用率。

它和 5.3.1 是同一家族的两种锚点：5.3.1 用实验测出的饱和平台值，5.3.2 用文档或实测的物理容量。容量随访问模式漂移时（内存带宽随读写比变化），用 5.3.1 更可靠；容量是物理常数时（端口线速），用 5.3.2 更干净。

**实例**（真实数据）：网口 p1_rx 实测 5.05 Gbps，端口速率 25 Gbps → n = 0.20。含义：入口走了线速的 20%。

#### 5.3.3 压力类——AF 占比（最硬的证据）

AF 类仪表（almost-full，接近满）记录的是"**缓冲占用达到或超过硬件阈值 θ 的周期数**"——像站台上的一盏警报灯，货堆高到警戒线就亮。MSS_NO_CREDIT、TDMA_RT_AF、TX_DAT_AF、RX_DAT_AF 都是这类。

```
n = AF_cycles / cycles
```

**含义**：警报灯亮着的时间占整个窗口的比例 = **队伍接近爆仓的概率**。用概率语言写：n = P(队长 ≥ θ)，即队长分布的尾部概率。

- n = 0：缓冲从未接近满（负载远未饱和）。
- n → 1：几乎每时每刻都在满的边缘（持续饱和）。

**为什么是最硬的证据**：这是硬件对队列状态的**直接观测**——不经过任何模型、不需要容量、不需要标定。DCTCP/DCQCN 等拥塞控制算法在交换机上用"队列深度越阈值的包被打标"来推断拥塞，AF 计数器就是 BF2 的硬件版 ECN 标记，只是把"每包打标"换成"每周期计数"。

**注意两点**：一是 θ 的具体值未知，所以 n 只能做序数比较（0.3 与 0.5 谁更饱和可比，但"θ 到底多满"不可知）；二是**我们的 MSS_NO_CREDIT 在 7 个应用里恒为 0，尚未证实它会动**——它的 n = 0 目前不能当作"无压力"的证据，只能当作"无观测"的默认值（详见 6.3 的可用性门槛）。

#### 5.3.4 忙闲类——EMPTY 取补（硬件直接报告的利用率）

EMPTY 类仪表记录的是"**缓冲为空的周期数**"——站台上的"空闲时间表"。REQ_BUF_EMPTY、WRQ_BUF_EMPTY 属于这类。

```
n = 1 − empty/cycles
```

**含义**：空着的时间占比取补 = 非空的时间占比 = **忙着的时间占比**。排队论语言：n = P(队长 ≥ 1)。单服务环节里"非空"就等价于"在干活"，所以忙占比**就是利用率本身**——硬件直接报告，不需要容量、不需要等待时间、不需要标定。

**它与 5.3.3 是同一支队伍的两台仪表**：AF 盯"快满"（高阈值 θ），EMPTY 盯"空"（阈值 1）。合起来能看出队形——忙占比高而 AF 占比低 = "一直在干活但从不积压"（舒适忙碌）；忙占比低而 AF 占比高 = "平时闲、来了就爆"（突发型压力）。

**实例**：xz 负载下 REQ_BUF_EMPTY 相对空闲期出现强负增量（−65.7M 周期/秒级），即"空着的周期变少了"——忙占比显著上升。精确比例待 P2 实现时从 CSV 计算。

#### 5.3.5 错误类——丢包率（旗标型信号）

```
n = drops / arrivals
```

drops 是丢弃/错误计数（丢包、重传），arrivals 是同窗口的流量计数。比值 = 丢失比例，天然 [0,1]。**丢包是队列溢出的终极信号**（DCTCP 同款思路）。

**性质**：旗标型而非平滑刻度——一秒窗口里大多数时候是 0；一旦非 0，就是强证据，在证据分级中压过一切。实例：N1 实测零重传 → n = 0（自洽）；E0-2 前向 62,910 次重传 → n 显著非 0（与"该路径高压丢包"判读一致）。

#### 5.3.6 效率类——miss 率（兜底公式）

```
n = 1 − hit_ratio = misses / (hits + misses)
```

当组件既没有 AF/EMPTY 仪表、又测不到容量/饱和参考时——L3 就是典型——退而求其次用**结构性占比**：未命中率本身就在 [0,1] 内。

**含义与局限**：未命中率高说明该组件没有接住流量（容量在失效），是效率信号而非利用率信号，所以排在证据分级最末、只做定性参与。

**实例**（真实数据）：BFS 负载下 L3 miss 41.1M ≫ hit 17.9M → n ≈ 0.70。含义："L3 对 BFS 的工作集基本失效"——这个数其实是下游内存环节压力的旁证。

### 5.4 统一视角：这些公式全在拍同一支队伍

把六种公式放进排队论框架，第一层做的事就非常清晰了：**每个组件前面有一支"队伍"（缓冲/流水线），队伍的状态由一个分布完全刻画——队长分布**。第一层的每个公式，都是在用可观测的计数器估计这个分布的某一个侧面：

| 公式        | 估计的量                   | 证据级别 |
| --------- | ---------------------- | ---- |
| AF 占比     | 尾部概率 P(队长 ≥ θ)（高阈值）    | 直接观测 |
| EMPTY 取补  | P(队长 ≥ 1)（低阈值，单服务即利用率） | 直接观测 |
| 容量归一化 λ/C | 利用率 ρ（容量锚点）            | 模型   |
| 跨度归一化     | 利用率 ρ（实验锚点）            | 模型   |
| 丢包率       | 溢出事件频率                 | 直接观测 |
| miss 率    | 服务效率                   | 兜底   |

对比 PathFinder：它用 λ×W 估计的恰恰是这个分布里**我们唯一拿不到**的那个量——**均值**（平均队长）。我们的第一层用尾部概率、利用率和效率替代均值，牺牲了"队长绝对值"，保住了"谁更接近饱和"的排序能力。这就是整个设计在无延迟计数器条件下的理论闭环。

## 6. 第二层详解：每个组件一个数

### 6.1 组件与面

一个组件（顶点）里有若干环节，每个计数器盯一个环节，称为一个**面**（facet）。例如 HNF 组件挂三块仪表：A72_ACCESS 盯"核请求到达面"，REQ_BUF_EMPTY 盯"请求缓冲队列面"，DIR_HIT 盯"目录命中面"。

第二层的任务：把这个组件上全部压力指数压成一个数：

```
v_j = max( n_c )，c ∈ 组件 j 的全部计数器
```

### 6.2 为什么取最大，而不是求和或求平均

**理由一：同一组件上的仪表，大多在探测同一支队伍。**

回顾 5.4 的分布观：AF 占比、EMPTY 取补、跨度归一化全是**同一个队长分布的不同函数**。HNF 的到达面和缓冲面盯的是同一条请求流水：到达得多 → 缓冲非空 → 忙占比高，两个指数高度相关。对同一个分布取多个函数，正确的聚合是**取最严峻的那个**，而不是相加——相加等于把同一支队伍的压力重复计算。最极端的反例就在我们的计数器清单里：L3 只有 HITS 和 MISSES，miss 率 + hit 率 ≡ 1，**若层内求和，L3 的 v 恒等于 1.0，任何负载下都满分**，完全退化。

**理由二：组件是串联结构，最紧的一环定生死。**

组件内部是"缓冲 → 仲裁 → 服务"的串行流水，串联系统的饱和语义是：**任何一个环节饱和，整个组件就饱和**（木桶原理）。到达面打到 0.9 而缓冲面只有 0.1——组件照样已经堵了。max 精确对应这个语义；均值会把 0.9 稀释成 0.5，掩盖"已堵"的事实。

**理由三：max 消灭了"仪表数量不公平"。**

各组件挂的仪表数量不齐（HNF 三块以上，L3 只有两块）。若求和，仪表多的组件天然占便宜；max 有一个好性质——**v_j 与挂多少仪表无关**（只要新增的不超过现有最大值）。第一层统一了"单位"，第二层统一了"观测密度"，两个不可比维度就此消灭。

### 6.3 证据分级：矛盾时信谁

第一层把每个指数分了证据级别：**压力类 > 忙闲类 > 频率类 > 效率类**（"直接观测"优于"模型推算"）。这个分级在第二层的作用**不是权重**——不搞"压力×0.9 + 忙闲×0.7"这种拍脑袋系数。它有两个用途：

**用途一：冲突仲裁。** 当同一组件的不同层级信号矛盾时，信更直接的观测。例：频率类说 n = 0.9（模型推算"快饱和了"）而忙闲类说 n = 0.05（硬件直接观测"缓冲几乎全空"）——矛盾本身是信息，大概率是 λ_sat 锚点标错了。仲裁规则：以忙闲类为准，**同时把矛盾记为校准警示**，回填校准表。

**用途二：来源标记。** v_j 的值从哪个层级来，就带哪个标签一起上报。第 3 层算完后，论文里可以如实报告："该路径的压力主要来自忙闲类直接观测，辅以频率类模型估计"——证据强度透明，每一个压力值都溯源到"什么在说话"。

**可用性门槛**：未证实的计数器不参与仲裁。MSS_NO_CREDIT 属于最高级（压力类），但恒为 0、未证实——它的 n = 0 不能用来压掉忙闲类的非零信号。一个从未动过的仪表给出 0，不是"无压力"的证据，只是"无观测"的默认值。未证实计数器先降为旁路信号，直到探针实验证实它真的会动。

### 6.4 伴随量：繁忙度

max 只回答"最紧的面有多紧"，丢掉了"其他面怎么样"的信息。所以每个组件配一个伴随量：

```
m_j = mean( n_c )   ← 组件繁忙度
```

两个量合起来，是 5.3.4 里"同一分布、两个阈值"思想在组件级的镜像——v_j 是最右移的边际（最紧的面），m_j 是平均位置（全面程度）：

| v_j（压力） | m_j（繁忙度） | 判读                   |
| ------- | -------- | -------------------- |
| 高       | 高        | 全面重载——所有面都接近饱和，真瓶颈候选 |
| 高       | 低        | 单点热点——只有一面爆，组件整体未饱和  |
| 低       | 高        | 均匀中等——全面忙碌但无饱和风险     |
| 低       | 低        | 空闲                   |

只有 max 没有 mean，就会把"单点热点"和"全面重载"混为一谈——这正是 PathFinder 里"停顿最大 ≠ 瓶颈"的教训（其 Case 4：某组件停顿 ×1.7 但占用反而下降）。

### 6.5 一个完整例子（HNF × xz，真实与示意数字混用、已标注）

- A72_ACCESS（频率类）：n = **0.34**（真实：见 5.3.1 的算式）
- REQ_BUF_EMPTY（忙闲类）：n ≈ **0.6**（示意——idle−app 差值已证实方向为正，精确比例待 P2 计算）
- DIR_HIT（效率类）：n ≈ **0.2**（示意，待核实）

```
v_HNF = max(0.34, 0.6, 0.2) = 0.6   来源标签：忙闲类（直接观测）
m_HNF = mean(0.34, 0.6, 0.2) ≈ 0.38
```

判读：HNF 整体中等偏忙（m = 0.38），但缓冲面单点接近饱和边缘（v = 0.6）——"单点热点"型，瓶颈风险在请求缓冲这一面。这个 v_HNF = 0.6 就是第 3 层累加时 HNF 这一项的贡献。

## 7. 第三层详解：路径总压力

### 7.1 主算子：求和

```
L_p = Σ v_j ，j ∈ 路径 p 上的全部组件
```

**为什么可加**：第一层已经把每个读数统一成"离饱和多远的百分比"——无量纲、都在回答同一个问题；第二层的 max 又保证每个组件只贡献一个数。所以跨组件求和是合法的：**路径的总压力 = 各环节压力之和**，就像旅途总耗时 = 各段耗时之和。

### 7.2 诚实声明：L_p 不是队长

L_p 是**归一化压力指数**——"这条路径的总压力足迹"，不是排队长度，不是 PathFinder 的"在途请求数"。它保证排序语义正确（谁更忙），但不提供队长绝对值，数值上也不可与 PathFinder 的 ΣQ 直接互比。论文与一切讲解中必须如实表述这一点。

### 7.3 共享组件怎么算：按入口比例分摊

MSS、tilenet、L3 等组件被多条路径共用。若把它们的 v_j 全量计入每一条经过的路径，压力会被重复计算。处理办法：**按各路径经该组件的入口流量比例分摊**（实现中称 M1 拆分，由 tools/path_data.py 维护映射，并用流量守恒校验：Σ 各路径分摊之和 = 组件总量）。

### 7.4 判定规则与伴随量

**判定：L_p 最大的路径 = 当前最繁忙路径。**

同时输出两个伴随量帮助解读：路径上 v_j 的**均值**（整体繁忙程度）与**最大值**（是否存在单点热点）。配合第 6.4 的四象限，回答"这条路径是全面重载还是单点热点"。

## 8. 为什么这些数字可以相加（可比性论证）

这一段是整套机制"合法性"的集中交代，讲解时值得单独强调。

**第一段：所有 n_c 都在回答同一个问题。** 无论原计数器的单位是次/秒、字节/秒还是周期数，第一层换算后，每个 n_c 的含义统一为"这一环离饱和还有多远"。回答同一个问题的数，才谈得上比较与相加——这就像"健康指数"把体温、血压、心率统一成同一尺度的评分。

**第二段：max 防止同一支队伍被重复计算。** 同一组件内多个计数器大多探测同一支队列，max 保证每支队列至多贡献一次（理由见 6.2）。

**第三段：Σ 只跨不同队列。** 不同组件的队伍相互独立（请求在这支队伍排完才进入下一支），压力相加不双计。

**与 PathFinder 的汇率对比**：PathFinder 靠 Little's Law 把队长统一成无量纲的"在途请求数"来求和；我们靠经验归一化把压力统一成 [0,1] 来求和。**汇率不同、量纲不同，数值不可互比；但"逐环节定量、沿路径累加、取最大排序"的机制哲学一致，排序语义一致。** 论文中应把这一对应关系如实写明。

## 9. 校准：让尺子读数可信

### 9.1 两套锚点

| 锚点          | 来源                                    | 现状                           |
| ----------- | ------------------------------------- | ---------------------------- |
| 空闲基线 λ_idle | 实验实测（负载前 5 秒空闲采样）                     | 已有（G 系列基线）                   |
| 饱和参考 λ_sat  | 应力标定（membench 打满内存、stress-ng 打满 L2 等） | 一次标定即可；初期用 bench 系列 CSV 回填初值 |

### 9.2 校准原则

- **定一次，长期用**：锚点是每个计数器的常数，标定后固化进配置表；只有怀疑失效时才重标。
- **失效的表现**：锚点标错，会表现为同一组件内不同层级信号矛盾（如 6.3 的例子）——仲裁机制会把它暴露为"校准警示"，这是模型自带的自检能力。
- **类比**：体温计出厂标定一次，之后每次测量直接读数；测量结果可疑时，再拿标准温度源复核。

### 9.3 待办

MSS_NO_CREDIT 等未证实计数器的探针实验（证实它确实会动）是校准工作的前置项，否则压力类证据始终缺位。

## 10. 验证：怎么证明模型是对的

**第一关（空载）**：空闲系统跑一遍，所有 n_c 应接近 0，所有 L_p 应接近 0。验证锚点与背景扣除是否正确。

**第二关（定向应力）**：单独打满某一资源（内存、L2、网口），对应路径的 L_p 应显著最大。验证"压力指数反映饱和逼近"的因果性。

**第三关（历史回放）**：用 G 系列与 E1 实验的既有 CSV 回放。这些实验已有独立判读结论：xz/BFS 压力在 CR 路径（核访存）、Redis 在 NAD 路径、iperf NHD 在 P5。检查三层索引的排序结果是否与这些既有结论一致——**纯本地、零设备依赖**，是成本最低的第一轮验证。

**第四关（退化检查）**：统计 v_j 的来源层级随负载类型的变化。若某计数器恒为 argmax（如 REQ_BUF_EMPTY 永远赢），需区分两种情况：该组件确有决定性瓶颈（可接受，但论文中如实写）；或其他计数器的锚点标定错误（需回炉校准）。若所有负载下来源层级毫无变化，说明融合机制没有真正起作用，等于退回单计数器判据——这正是设计过程中被纠正过的那一版方案的坑，验证必须守住这条线。

## 11. 边界：这个模型不做什么

**不做顶点级定位。** 本模型回答"哪条路径最忙"，不回答"这条路径上哪一环堵"。后者需要延迟类观测，留未来。

**不做延迟类分析。** 探针测等待时间（Q_wait = λ×(W_load−W_idle) 一类方法）需要 W 标定实验，整体留未来。

**证据覆盖不全，如实标注。** 背压类直接观测只覆盖约半数转发点；其余环节靠频率/效率类兜底，证据级别弱。每个 v_j 的来源标签如实上报，论文中按覆盖率表披露。

**不承诺队长真值。** L_p 是压力指数不是队长（见 7.2）。

## 12. 讲解指南：怎么把这个模型讲给别人听

### 12.1 一句话版

"我们把网卡里各条数据路径上的全部计数器，统一换算成 0–1 的压力值（离饱和还有多远），每个组件取最紧张的那个面，再沿路径累加——压力总和最大的路径，就是当前最繁忙的路径。"

### 12.2 三分钟版（四步）

1. **问题**（30 秒）：数据在网卡里走固定路径、经过一串组件；我们要判定哪条路径最繁忙（= 最接近容量极限）。
2. **为什么难**（40 秒）：最直观的办法是看排队长度，但硬件没有队长/等待时间计数器；用公式推队长需要等待时间，也没有；比流量又不公平（路径容量不同）。所以退一步——**不需要知道队伍多长，只需要知道谁离撑爆最近**。
3. **做法**（60 秒）：三层机制——第一层给每个计数器配 0–1 压力刻度（空闲/饱和两个锚点标定）；第二层每个组件取最大（同一支队伍的多台仪表看最严峻的，串联最堵的一环定生死）；第三层沿路径求和，最大者就是最繁忙路径。
4. **诚实声明**（30 秒）：这个指数是"压力百分比"不是队长；证据分级透明，直接观测优先于模型推算；顶点级定位和延迟方法留未来。

### 12.3 三十分钟版

按本手册第 1–8 章顺序讲，重点停两处：**第 2 章**（三条直觉路线的失败——听众最容易在这产生"为什么不直接看队长/流量"的疑问，先发制人）；**第 5 章**（第一层——六种公式是全部技术含量所在，务必用快递分拣中心的比喻逐个过）。第 8 章（可比性）单独强调一次，因为"为什么这些数能加"是审稿人和答辩评委最可能追问的点。

### 12.4 高频问答预案

**Q1：为什么不直接量排队长度？**
A：硬件没有队长/等待时间计数器，这是事实约束。PathFinder 的时间账本依赖等待时间，不可移植；我们的整个设计就是对这一缺失的正面应对。

**Q2：取 max 会不会太简单、丢信息？**
A：同一组件的多块仪表大多探测同一支队伍，对同一分布取多个函数，正解就是取最严峻者；反例：L3 的 hit 率 + miss 率 ≡ 1，若求和则恒为 1 完全退化。信息没有丢——伴随量 mean 并行输出，区分"全面重载"与"单点热点"。

**Q3：归一化的锚点从哪来？标错了怎么办？**
A：空闲基线实测已有；饱和参考应力标定一次、bench 数据回填初值。锚点错误会表现为同一组件内不同层级信号矛盾，仲裁机制按"直接观测优先"裁定并记录校准警示——模型自带自检。

**Q4：可信度如何保证？**
A：三层设计保证全量计数器参与（不是单计数器判据）；证据分级让每个数值可溯源；四关验证（空载/应力/历史回放/退化检查）闭环。

**Q5：和 PathFinder 什么关系？**
A：借 ΣQ 的"逐环节定量、沿路径累加、取最大排序"哲学与 PFAnalyzer 的占用账本定位；弃 PFEstimator 的时间账本（依赖等待时间）。量纲不同（归一化压力 vs 在途请求数），数值不可互比，排序语义一致。

**Q6：为什么只做路径级、不做顶点级定位？**
A：背压计数器只覆盖约半数转发点，延迟计数器缺失会使顶点级方法产生结构性偏差。范围裁定：先把路径级做扎实，顶点级与延迟方法留未来。
