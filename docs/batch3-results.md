## 2. 核心成果

### 2.1 c5b：四路 GUPS 份额分解（PASS）

四实例（表 64MB/256MB/1GB/2GB，各钉一核）并发 60s，判决 dominant cr 1.791。
GUP/s 为 0.011/0.007/0.004/0.002，**份额 45.8%/29.2%/16.7%/8.3%，随表尺寸
单调递减**——表越大、单次更新的 DRAM 延迟越高、速率越低，PathFinder 式
"吞吐↔带宽份额"对照成立。聚合 0.024 GUP/s 高于单跑标定 0.018（四核并行摊薄
延迟）。注：ib=1.000 为 M1 份额路由伪影（同 c4c），入模型口径账，不阻塞。

### 2.2 c5a（run2）：梯度对照交付 + 并发核心切片取证（A 类闭合）

**应用层（四日志，全部跑完）**：2.6K / 9.6K / 90.4K / 98.4K ops/s——缓存尺寸
16M/64M/256M/1G 对应的吞吐梯度 **38×**。两个大缓存实例（块缓存自足）跑在内存档
≈100K（≈m1 基线 110K）；两个小缓存实例（块缓存只装 0.8%/3.2%）落 eMMC 档。
机理：副本 8GB 压着 9.2GB 可用内存的边，cp 的脏页回写又挤压页缓存——小实例的
读只能排队等 eMMC。与 c1e（64MB 档 eMMC 速度）互证。

**计数器层（切片取证，A 类核心）**：四路并发只持续 ~9s（大缓存实例跑完即退场，
db256 8.8s / db1g 16s / db64 42s / db16 77s——"读量按缓存反比配平"配的是公平
不是等时长，38× 速率差把时长差拉成了 8.8s-77s），全窗 78s 的均值被 70s 单实例
eMMC 涓流稀释：

| 段 | 时长 | a72（聚合） | mem_reads | 说明 |
|---|---|---|---|---|
| 4-way 并发 | 0-9s | **17.34M/s** | 11.73M/s | =2.7× c3e 单实例（6.49M/s） |
| 3-way | 9-16s | 6.59M/s | 6.10M/s | db256 退场 |
| 2-way | 16-42s | 1.49M/s | 0.91M/s | db1g 退场 |
| 1-way | 42-78s | 1.12M/s | 1.06M/s | 仅 db16（eMMC 档 2.6K ops/s） |
| **全窗** | 78s | 3.39M/s | 2.53M/s | 引擎判 low 的依据 |

**引擎自洽性检查（非缺陷）**：cr 比值 c5a/c3e = 0.200/0.385 = 0.52，a72 比值
3.39/6.49 = 0.52——线性吻合，引擎按窗口均值如实判 low，只是窗口口径"看不见"
9s 的并发核心。另：io_write 全程 ~97K/s = 8GB 副本脏页回写 + 小实例 eMMC 读，
io 域其实全程在忙（对 eMMC 档实例而言 eMMC 就是公共瓶颈，但路径模型对存储域
无覆盖——缺口第 4/5 次现身）。

**A 类两处修订**：①设计假定"四副本全内存驻留"部分落空（RAM 边缘+回写挤压），
实测梯度反而更陡（38×），份额对照判别力更强；②"读量反比配平"未配平等时长，
并发核心短命 → 判决需切片取证 + 改进项"峰值窗口口径"（§4）。

### 2.3 c6a：出向 TCP 压载（A 类准 PASS，nad 头名修订）

判决 dominant nad 0.287 / ih 0.099（期望 dominant ih，照抄 E2 签名）。流量
真实：en3f1_rx **170.6MB/s ≈ 1.36Gbps**（出向，方向语义同 E2）、pcie1_tx
185.2MB/s、p1_tx 66B/s（未用）、tile 域 a72 1.79M/s / io_reads 0.46M/s
（TX 走 DMA，A72 参与低——与 c6c 的 3.67M/s 对照合理）。

**头名修订（A 类）**：翻三档出向轮次的完整谱系——c6a 1.36Gbps：nad 0.287
领跑；E2 armsend 6.6Gbps：arm 顶点饱和（n=0.967）→ 份额路由把 ih 顶到
1.000/nad 0.980 近平局；c2b 11.3Gbps 饱和档：漂到 nad 1.566/ih 1.067。
**ih 拿头名只在 arm 顶点饱和档出现**（M1 份额路由产物）；未饱和档的自然头名
= nad。判读标准按此修订。

**新账目**：pcie0_tx 186.1MB/s ≈ pcie1_tx 185.2MB/s ≈ en3f1_rx 170.6MB/s
三方 1:1 镜像——Arm→网络出向流同时点亮两套 pcie 计数（与 c2b 的"pcie1_tx
计入穿透 TLP"同族怪癖），并入"pcie0_tx 53M/s"未解账（该账目首次拿到同流
对照数据）。

### 2.4 c6c/c6d：判决同 low、raw 可分离（A 类，机制切换证据完整）

两轮均判 low——批次二已证 eMMC 档负载比内存/网络锚点低 2-3 个数量级，判 low
是诚实的答案（风险注已预告）。**判读目标（buffered↔direct 机制切换）在 raw
计数器层完整成立**：

| 计数器 | c6c buffered | c6d direct | 解读 |
|---|---|---|---|
| a72_access | 3.67M/s | 2.70M/s（−27%） | direct 少了页缓存路径的 CPU 活 |
| mem_reads | 1.77M/s | 0.82M/s（**−54%**） | buffered 的页缓存拷贝分量（2.15×） |
| io_reads | 7.4K/s | 7.2K/s（持平） | 同一批 eMMC 读，一个不多一个不少 |
| io_write | 375K/s | 287K/s | =设备视角 eMMC 读（0x73/0x74 语义）；buffered 更高 = 预读多拉 |

"判决同 low、raw 可分离"本身即论文素材：模型边界（存储域无覆盖）与计数器判别力
（机制切换可见）在同一对轮次里同时成立。

## 3. C 类记录（均已定位）

### 3.1 c5a run1：LevelDB LOCK 互斥（设计缺陷）

三实例开库即死，db16.log 原文："open error: IO error: lock
/root/bf2k/data/dbtest/LOCK: Resource temporarily unavailable"。LevelDB 的
LOCK 文件是互斥锁，四进程不能同开一个库。仅 1G 缓存实例跑完 75s（45.9µs/op，
eMMC 档，与 c1e 同档）。修复：四份独立库副本（cp 经页缓存驻留 → 免
drop_caches）+ 窗长 300s + 期望修订 dominant cr 或 multi → run2 四实例全部
跑完（§2.2）。

### 3.2 c6b run1/run2：app 相位两次都是 1s

run1（sockperf --udp）秒退；run2 同样 1s。CSV 取证：1s 内仅进程启动脉冲
（a72 突发 ~1.5M），**零网络字节**（各口 <1KB/s 背景）——客户端在发送任何
UDP 之前就死了。最可能根因（按可能性排序）：①fujian 端 netserver 已死
（批次 0 是 9/23 起的，设备可能重启过），netperf 控制连接被拒；②若走的是
sockperf 路线①，服务端仍为 TCP 模式未改。**待用户提供当时终端报错原文 +
fujian 端 `pgrep -a netserver; pgrep -a sockperf` 输出**，再跑 run3（netserver
死则 `netserver -D -4` 后重跑路线②；服务端未改则重启 `sockperf sr --udp`）。

## 4. 对模型意味着什么（引擎评估）

- **判决层 0 引擎缺陷（B 类）**：c5a 的 low 与窗口物理完全自洽（cr 比值= a72
  比值= 0.52 线性吻合）；c6b 两次 low 是数据问题（app 没跑起来），非引擎错。
- **A 类 4 处全部有物理解释**：c6a 头名谱系修订（nad 未饱和档领跑）；c5a 内存
  驻留假定 + 等时长配平两处；c6c/c6d 风险注坐实。
- **改进项（未来，不阻塞）**：① 引擎增加**峰值窗口口径**（如 max-10s 均值或
  滑动窗 max）以捕捉短并发核心——c5a 的 4-way 段（a72 17.3M/s）被 78s 窗均值
  稀释 5×；② eMMC/存储域路径覆盖缺口第 4/5 次现身（c5a 小实例、c6c/c6d），
  论文模型边界段证据齐；③ pcie0_tx 镜像新账目（同流对照首次拿到）；④ M1 份额
  伪影再证（c5b ib=1.000）。
- **论文素材**：c5b 份额-表尺寸单调律（PathFinder 同构表格）；c6a→E2→c2b 的
  头名-速率谱系（模型边界精确化）；c6c/c6d 机制切换 raw 对照表；c5a 的 38×
  缓存梯度 + 切片取证方法（峰值窗口口径的动机）。
