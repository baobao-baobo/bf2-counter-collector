# BFS 路径搜索设计（繁忙路径判定 + 实例验证）

版本 2026-09-20。本文档定义三层索引引擎之上的**搜索层**——"BFS 算法"的
完整规格：搜索空间、判定规则、证据链输出、实例验证协议、实现形态。
前置：`docs/bf2-bottleneck-queueing-model.md`（§4.6 三层索引）、
`docs/bf2-pf-execution-plan.md`（M4 已通过）、`docs/validation-replay.md`
（§7 锚点替换后三关状态）。

## 0. 定位与目标

三层计算引擎已存在（`tools/analyze_bottleneck.py`）并通过回放关验证
（17/17，锚点替换后 2026-09-20 复验）。本文档不重造引擎，只定义：

> **给定一个负载场景（若干采集快照组成的窗口），回答一个问题：当前
> 哪条数据路径最繁忙？——并给出可解释的证据链。**

与模型文档二轮修订的设计目标一致：路径级繁忙度判定；顶点级瓶颈定位
与延迟归因留未来（§4.5 边界、未来工作清单）。"BFS"在此 = 沿路径图
自入口向出口逐顶点推进的压力累加搜索，每次运行输出一个场景判决。

## 1. 搜索空间：路径图（已定设计点 1）

**不新造图**。搜索空间 = `configs/path_table.conf` 既有的 12 顶点、
7 路径（入口 → 出口方向）：

| 顶点                      | 域                          | 状态                     |
| ----------------------- | -------------------------- | ---------------------- |
| hnf / l3 / mss / arm    | 核访存域                       | ✅ 有锚点                  |
| tilenet / smmu / trio   | 互连/IOMMU/内部总线              | ⚠️ 零值悬置（不参与仲裁）         |
| pcie0                   | 主机面（Gen3 x16 实测 15.75GB/s） | ✅ cap 锚点               |
| pcie1                   | Arm 子系统（Gen4 x16 31.5GB/s） | ✅ cap 锚点               |
| eswitch / wire / pf1hpf | 网域                         | ✅ cap 锚点（wire=100G 实测） |

| 路径  | 入口 → 出口                         | 判读基准                    |
| --- | ------------------------------- | ----------------------- |
| cr  | 核 → L3 → DDR（core read）         | xz/BFS/BS/SQLite/TFLite |
| ih  | 主机 → PCIe → DDR（ingress host）   | pcie0 收                 |
| ib  | Arm → PCIe → 主机（ingress bridge） | pcie0 反向                |
| wb  | 核 → L3 写回（writeback）            | 写应用                     |
| nad | 网口 → Arm 终接（network to Arm DMA） | Redis/iperf 终接          |
| nhd | 网口 → 主机直通（network to host DMA）  | NHD 直通流                 |
| tx  | 核 → 网口发送（TX 路径）                 | p7/上传流                  |

四类诚实盲点（无硬件计数器，搜索输出必须显式声明而非静默跳过）：
L3 内部队列压力、PCIe TLR 队列、eSwitch 内部队列、Arm 软件队列。
对应处置 = 这些环节的压力只能由上下游计数器旁证（设计手册 §4.5
边界、覆盖率披露），在证据链中标注 `[盲点旁证]`。

## 2. 三层计算（复用引擎，不重写）

每快照（1s 全计数器行）：

1. **计数器归一化** n_c ∈ [0,1]：六族公式（span/cap/af/empty/drops/miss），
   锚点来自 `configs/anchor_idle.conf` + `anchor_sat.conf`；sat 锚点两档
   质量（真应力 vs obs-max 下界）在证据链中如实标注 provenance。
2. **顶点融合** v_j = max(n_c)，伴随均值 m_j 与证据标签（来源计数器 +
   家族）；`[unverified]` 计数器算出但不参与仲裁（可用性门）。
3. **路径累加** L_p = Σ v_j（共享顶点按入口速率份额拆分，M1 机制）。

证据层级（仅 provenance 标注，不参与权重）：压力(af/empty) > 忙闲
(span/cap) > 频率(drops) > 效率(miss)。

## 3. 搜索算法（场景级，已定设计点 2）

输入 = 场景窗口（一个或多个 CSV 的负载行，相位日志界定）。算法：

1. 逐快照计算 7 条路径的 L_p（引擎 `run_one` 已有形态）；
2. **双判据聚合**：
   - **幅度判**（med）：窗口内 L_p 的中位数 argmax——对应核访存域
     （混合流下 CR 计数器承载 NAD 的 DDR 跳，设计文档 §8.5）；
   - **方向判**（wins）：逐快照 argmax 路径的得票——对应网域/主机域
     （方向性证据）；
3. **判决规则**（回放关已固化的三条规则形式化）：
   - 主导判：judge == 期望路径 且 med 居首 → 判定该路径最忙；
   - 低载判：期望为低载场景时，med 首位 < 0.2 或无多数得票
     （wins 首位 < 50%）→ 判定"无强主导"（e1_g7 cr 36:nad 35 先例）；
   - 平局判：上一条的多数条款（2026-09-20 加入，见 validation-replay
     §7.3）。

## 4. 输出与证据链（已定设计点 3）

每次搜索输出（文本报告 + JSON 证据，JSON 为论文图表素材）：

1. **判决**：最繁忙路径 + 置信形态（主导/低载无强主导/平局）；
2. **路径排序**：7 条 L_p 中位数表；
3. **顶点贡献分解**：繁忙路径上逐顶点 v_j 及来源计数器（该计数器的
   n、provenance 档位）——"为什么判它忙"的直接答案；
4. **警示**：仲裁矛盾（同顶点跨层级证据冲突）、退化统计（argmax 层级
   分布）、SAT-SUSPECT（顶点 argmax 期间 n 均值 ≥0.85）、
   `[盲点旁证]` 标记、`[unverified]` 悬置声明。

## 5. 实例验证协议

**实例集 A（历史回放，17 个已知答案）**：G 系列 ×7 + E1 ×4 组 +
主机定标 3 + iperf 梯度 4 + eMMC 负例。搜索输出必须与
`replay_validate.py` 三关结论逐例一致（回归闸）。

**实例集 B（sat 六面，合成已知答案）**：p1–p7 六面本身作为实例输入，
每个面的资源取向即期望答案：

| 面                | 期望判决                                                               | 判据  |
| ---------------- | ------------------------------------------------------------------ | --- |
| p1 stress-ng cpu | CR 居首（弱面，L_p 量级低）                                                  | 幅度判 |
| p3 STREAM        | CR 居首（emem 读+写全压）                                                  | 幅度判 |
| p4 memrand       | CR 居首（随机访存）                                                        | 幅度判 |
| p5 cache thrash  | CR 居首（最强面）                                                         | 幅度判 |
| p6 fio eMMC      | **全路径低位 = 诚实负例**（eMMC 无计数器，覆盖缺口应"看不到"）                             | 幅度判 |
| p7 iperf3        | CR 居首（TX DMA 读跳——tile_io_reads n≈1.0，io_reads=TX 速率已实证；出口不可观察，见下注） | 幅度判 |

> **p7 修正（2026-09-22）**：p7 CSVs（bench_p7_net.conf）无每口列（早于
> 8ff40c4 特性），TX/NAD/NHD 出口入口列缺失 → 出口路径不可观察；且
> p7 上传（Arm→主机）根本不经过 wire 口 p1。实际判决 CR 居首，来源 =
> TX DMA 读跳（tile_io_reads n≈1.0，混合流表现，与 NAD 的 DDR 跳同构，
> 模型文档 §8.5）。Arm→主机出口路径不在路径模型中 → 未来工作（§7）。
> 实现已同步：tools/bfs_search.py 的 SAT_EXPECT p7 = ("cr", False, ...)。

**新增实例协议**：任何新场景（设备线新采集）入库后：跑搜索 → 记录
判决 + 判读 → 并入实例表。实例表是论文"模型验证"章节的素材直接来源。

## 6. 实现形态

`tools/bfs_search.py`：编排层（~150 行），复用 `analyze_bottleneck` 的
`load_model` / `Run` / `Analyzer` / `run_one`，不复制引擎逻辑。

```
用法：python tools/bfs_search.py <csv...> [--scene NAME] [--json out.json]
输入：场景 CSV（+ 可选 .phase.log 界定窗口；无相位日志按 5s 前后裁剪）
输出：stdout 判决报告（§4 四件套）+ 可选 JSON 证据
回归：python tools/bfs_search.py --selfcheck
     = 内置断言：实例集 A 判决 == replay_validate 结论；实例集 B 六面
       判决 == §5 表（作为 CI 型回归闸）
```

## 7. 边界声明（写进论文的诚实披露）

- 顶点级瓶颈定位（"哪一级队列堵了"）不在本搜索范围——背压计数器仅
  覆盖约半数转发点且无延迟计数器，属未来工作；
- sat 锚点两档质量：14 真应力 / 36 下界——下界锚点的顶点饱和读数
  （n≈1）需谨慎判读（SAT-SUSPECT 机制已内建）；
- 四类硬件盲点由上下游旁证，输出显式标注；
- **Arm→主机出口路径缺失**（p7 上传流）：路径模型只有核→网 TX 出口
  （p1_tx_bytes），Arm 软件发起、经 DMA 读入再上行的出口（网口零列
  可观察的配置下）无对应路径——覆盖缺口，未来工作。
