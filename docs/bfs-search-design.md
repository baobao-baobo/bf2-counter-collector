# BFS 路径搜索设计（繁忙路径判定 + 实例验证）

版本 2026-09-20。本文档定义三层索引引擎之上的**搜索层**——"BFS 算法"的
完整规格：搜索空间、判定规则、证据链输出、实例验证协议、实现形态。
前置：`docs/bf2-bottleneck-queueing-model.md`（§4.6 三层索引）、
`docs/bf2-pf-execution-plan.md`（M4 已通过）、`docs/validation-replay.md`
（§7 锚点替换后三关状态）。

## 0. 定位与目标

三层计算引擎已存在（`tools/analyze_bottleneck.py`）并通过回放关验证
（17/17，锚点替换后 2026-09-20 复验）。本文档不重造引擎，只定义：

> **给定一个负载场景（若干采集快照组成的窗口），回答一个问题：当前
> 哪条数据路径最繁忙？——并给出可解释的证据链。**

与模型文档二轮修订的设计目标一致：路径级繁忙度判定；顶点级瓶颈定位
与延迟归因留未来（§4.5 边界、未来工作清单）。"BFS"在此 = 沿路径图
自入口向出口逐顶点推进的压力累加搜索，每次运行输出一个场景判决。

## 1. 搜索空间：路径图（已定设计点 1）

**不新造图**。搜索空间 = `configs/path_table.conf` 既有的 12 顶点、
7 路径（入口 → 出口方向）：

| 顶点                      | 域                          | 状态                     |
| ----------------------- | -------------------------- | ---------------------- |
| hnf / l3 / mss / arm    | 核访存域                       | ✅ 有锚点                  |
| tilenet / smmu / trio   | 互连/IOMMU/内部总线              | ⚠️ 零值悬置（不参与仲裁）         |
| pcie0                   | 主机面（Gen3 x16 实测 15.75GB/s） | ✅ cap 锚点               |
| pcie1                   | Arm 子系统（Gen4 x16 31.5GB/s） | ✅ cap 锚点               |
| eswitch / wire / pf1hpf | 网域                         | ✅ cap 锚点（wire=100G 实测） |

| 路径  | 入口 → 出口                         | 判读基准                    |
| --- | ------------------------------- | ----------------------- |
| cr  | 核 → L3 → DDR（core read）         | xz/BFS/BS/SQLite/TFLite |
| ih  | 主机 → PCIe → DDR（ingress host）   | pcie0 收                 |
| ib  | Arm → PCIe → 主机（ingress bridge） | pcie0 反向                |
| wb  | 核 → L3 写回（writeback）            | 写应用                     |
| nad | 网口 → Arm 终接（network to Arm DMA） | Redis/iperf 终接          |
| nhd | 网口 → 主机直通（network to host DMA）  | NHD 直通流                 |
| tx  | 核 → 网口发送（TX 路径）                 | p7/上传流                  |

四类诚实盲点（无硬件计数器，搜索输出必须显式声明而非静默跳过）：
L3 内部队列压力、PCIe TLR 队列、eSwitch 内部队列、Arm 软件队列。
对应处置 = 这些环节的压力只能由上下游计数器旁证（设计手册 §4.5
边界、覆盖率披露），在证据链中标注 `[盲点旁证]`。

## 2. 三层计算（复用引擎，不重写）

每快照（1s 全计数器行）：

1. **计数器归一化** n_c ∈ [0,1]：六族公式（span/cap/af/empty/drops/miss），
   锚点来自 `configs/anchor_idle.conf` + `anchor_sat.conf`；sat 锚点两档
   质量（真应力 vs obs-max 下界）在证据链中如实标注 provenance。
2. **顶点融合** v_j = max(n_c)，伴随均值 m_j 与证据标签（来源计数器 +
   家族）；`[unverified]` 计数器算出但不参与仲裁（可用性门）。
3. **路径累加** L_p = Σ v_j（共享顶点按入口速率份额拆分，M1 机制）。

证据层级（仅 provenance 标注，不参与权重）：压力(af/empty) > 忙闲
(span/cap) > 频率(drops) > 效率(miss)。

## 3. 搜索算法（场景级，已定设计点 2）

输入 = 场景窗口（一个或多个 CSV 的负载行，相位日志界定）。算法：

1. 逐快照计算 7 条路径的 L_p（引擎 `run_one` 已有形态）；
2. **双判据聚合**：
   - **幅度判**：窗口内 L_p 的**均值**（多 CSV 取各 CSV 均值的中位）
     argmax——对应核访存域（混合流下 CR 计数器承载 NAD 的 DDR 跳，
     设计文档 §8.5）。2026-09-22 由中位数改为均值：突发场景（E2E B/C，
     10s 洪流落在 30–46s 窗内）逐行中位数被空载行稀释到 0，均值保留
     突发信号；顶点贡献分解同步改均值（见 §4.3）。
   - **方向判**（wins）：逐快照 argmax 路径的得票（VOTE_FLOOR 弃权）
     ——对应网域/主机域（方向性证据）；
3. **判决规则**（2026-09-22 E2E 后三值化）：
   - **dominant**：med 首位 ≥ 0.2 且 wins 首位过半数 → 判定该路径最忙；
   - **low**：med 首位 < 0.2 → 整体低载，无繁忙路径；
   - **multi**：med 首位 ≥ 0.2 但 wins 首位未过半数 → 多路径繁忙、
     无单一主导（e1_g7 cr 36:nad 35 平局先例的推广；E2E C 混载
     cr 0.584 且 14/35 票，2026-09-22 之前被误标 low）。低载平局
     （e1_g7 级别幅度）仍落 low 分支，回放闸多数条款不变
     （replay_validate.py 第 150 行）。

## 4. 输出与证据链（已定设计点 3）

每次搜索输出（文本报告 + JSON 证据，JSON 为论文图表素材）：

1. **判决**：最繁忙路径 + 置信形态（dominant/low/multi 三值）；
2. **路径排序**：7 条 L_p 窗口均值表（多 CSV 取中位）；
3. **顶点贡献分解**：繁忙路径上逐顶点 v_j 窗口均值及来源计数器（该
   计数器的 n、provenance 档位）——"为什么判它忙"的直接答案；
4. **警示**：仲裁矛盾（同顶点跨层级证据冲突）、退化统计（argmax 层级
   分布）、SAT-SUSPECT（顶点 argmax 期间 n 均值 ≥0.85）、
   `[盲点旁证]` 标记、`[unverified]` 悬置声明。

| ---------------- | ------------------------------------------------------------------ | --- |

| p3 STREAM        | CR 居首（emem 读+写全压）                                                  | 幅度判 |
| p4 memrand       | CR 居首（随机访存）                                                        | 幅度判 |

## 7. 边界声明（写进论文的诚实披露）

- 顶点级瓶颈定位（"哪一级队列堵了"）不在本搜索范围——背压计数器仅
  覆盖约半数转发点且无延迟计数器，属未来工作；
- sat 锚点两档质量：14 真应力 / 36 下界——下界锚点的顶点饱和读数
  （n≈1）需谨慎判读（SAT-SUSPECT 机制已内建）；
- 四类硬件盲点由上下游旁证，输出显式标注；
- **Arm→主机出口路径缺失**（p7 上传流）：路径模型只有核→网 TX 出口
  （p1_tx_bytes），Arm 软件发起、经 DMA 读入再上行的出口（网口零列
  可观察的配置下）无对应路径——覆盖缺口，未来工作。

## 8. 繁忙路径的瓶颈顶点归因（P2.5b）

判决出"最繁忙路径"之后，把该路径的繁忙指数**分解回顶点**，按贡献
排名输出头号顶点。口径与行 L_p 严格对齐：

- **贡献 c = 顶点值 × M1 份额**，对负载窗内每一行求均值。某顶点在
  某行不可观测（该行未经过它）时按 0.0 计入该行（全支撑口径），使
  "各行贡献之和 == 该行 L_p"、进而"平均贡献之和 == 行均值 L_p"恒
  成立（自检 C 门 1）。
- **稳定性 = 该顶点在本路径行内登顶的次数 / 有登顶者的行数**——顶
  点可能稳居第一，也可能与并列头部交替登顶（如 HTTP 场景 arm 与
  eswitch 各约 48% 贡献的近平局，stability 9/11 对 0/11 才能区分）。
- 逐顶点附：锚点来源（真应力/下界）、观测标签、样本数；下界锚点
  顶到头的顶点打 `[SAT-SUSPECT anchor]` 标记。
- **口径声明（必须随输出出现）**：这是模型口径的贡献排名，不是因
  果定位——背压计数器覆盖缺口与锚点来源限制一并在 §7；路径总 L_p
  高只说明"该路径上被观测的顶点整体读数高"。
- low 判决下不输出归因（安静场景没有繁忙路径，保持诚实负例）。

### 8.1 全局顶点压力排序与分歧提示（P2.5d）

路径判决与归因只覆盖胜者路径；用户场景：某非胜路径顶点的读数可能
高于胜者路径的头号贡献顶点（路径 L_p 是"和"，顶点 v 是"单项"，
两者本来就不同质）。因此新增第三块输出——**全局顶点压力排序**：

- 排序键 **v = 顶点原始读数在观测行上的均值**（观测行口径：从
  不触发的顶点没有读数，补 0 会把观测盲区伪造成"不重要"，故不
  用全支撑口径；全支撑口径只为归因对账服务）；
- 每行附：观测行数 obs/总行数、**flow = 收到该顶点最大平均贡献
  的路径**（贡献用全支撑口径，与归因同尺）、所属路径集合、主导
  计数器标签、锚点来源与 SAT-SUSPECT 标记；
- **分歧提示**（只提示、绝不改判）：N1 全局头名的 flow 不在胜者
  路径上 → "峰值流向非胜路径"；N2 全局头名不是胜者头号贡献顶点
  且 v 严格大于后者 c → "读数超过胜者头号贡献"。当前三个场景均
  不触发（sort 的 mss v=0.113 对 cr 头号 l3 c=0.115 仅 98%），
  触发路径由合成用例自检（C5）覆盖；
- 与 P2.5b 的差别：P2.5b 回答"胜者路径的繁忙由谁构成"（c 口径，
  按路径内排名）；P2.5d 回答"哪个观测点离自己的饱和参照最近"
  （v 口径，跨路径排名）。共享顶点 v 高不必然意味着它对胜者路径
  贡献大（sort 的 mss：v=0.113、落 cr 仅 0.072、主流量在 ib）
  ——两口径必须同列展示，取头名当"路径瓶颈"会张冠李戴。

## 9. 双面板路径压力图（P2.5c，gnuplot）

同一张图并排**幅度判定**与**方向判定**，共享横轴（cr/ih/ib/wb/
nad/nhd/tx 七路径）：

- 上板：各路径 L_p 窗口中位数柱 + 0.2 判定地板虚线；幅度胜者
  深红 #B2172B，其余灰 #D0D0D0，柱顶标值。
- 下板：各路径行胜票数柱 + 过半数虚线；方向证据（wins leader）
  浅橙 #F5A682，柱顶标票数。
- 判决与证据并入标题（如 `dominant nad (med 0.257, wins nad=8/11)`），
  标题即结论；house 样式（四边框、键居外上、无顶/右刻度）。
- 两判定分离的动机：e4_http_run2 中 nad 幅度 0.257 与 cr 0.238 仅
  差 0.019（幅度近平局），方向 8/11 票才分出胜负——两板并置把
  "幅度多高"与"方向多一致"两个正交问题同时回答。
- 实现注意：本机 gnuplot 6.0.4（Windows）不按空行分块——`index`
  /`every` 跳过式读取恒空，故每面板各写一个单块数据文件
  （PREFIX_mag.dat / PREFIX_dir.dat），plt 内路径一律正斜杠
  （反斜杠会被当转义符）。
