# iperf3 系统学习文档

> **定位**：简历可写、面试可答的水平。iperf3 是网络性能测试的事实标准工具，测吞吐、丢包、抖动、双向并发都用它。
> **使用环境**：本文命令以 Linux 为主（你的实验环境是 BF2 / 服务器）。Windows 也有官方二进制版，但性能测试结果解读时要考虑 Windows 网络栈差异。
> **配套知识**：TCP 拥塞控制、BDP（带宽延迟积）、网卡 offload——§3 会讲清这些基础，这是和"只会敲命令"拉开差距的地方。

## 1. iperf3 是什么

- **iperf3 是测量两台主机之间 TCP/UDP 吞吐量的标准工具**，由 ESNET（美国能源部科学网络）开发维护。数据中心网络验收、链路排障、SD-WAN 测试都在用。
- 架构是 **C/S 模型**：一台机器跑服务端（`iperf3 -s`），另一台跑客户端（`iperf3 -c server_ip`），客户端主动连服务端，测完报告结果。
- 默认测 **TCP 单向吞吐**：客户端→服务端方向，跑 10 秒。
- **iperf2 与 iperf3 是两个独立项目，不兼容**（经典坑）：

|         | iperf2 | iperf3          |
| ------- | ------ | --------------- |
| 默认端口    | 5001   | **5201**        |
| 线程模型    | 多线程    | 单线程/每流          |
| 同时双向    | `-d`   | `--bidir`（3.7+） |
| 多播测试    | 支持     | 不支持             |
| JSON 输出 | 无      | `-J` 原生支持       |
| 维护方     | 社区     | ESNET           |

客户端和服务端版本不匹配（iperf3 客户端连 iperf2 服务端）会握手失败——排查问题时先查双方版本。

## 3. 网络吞吐测试基础（★ 面试重点）

### 3.1 iperf3 测的是什么：goodput 而不是线速

- **线速（line rate）**：物理层比特率。10G 链路 = 10¹⁰ bit/s = **1.25 GB/s**。
- **iperf3 测的是应用层有效吞吐（goodput）**：TCP 载荷字节数/时间，不含以太网帧开销（前导码 8B + 帧间隙 12B + FCS 4B + 以太网头 14B ≈ 每帧 38B 开销）、IP 头（20B）、TCP 头（20B）。
- MTU 1500 时每帧载荷 1460B，开销占比约 66/1518 ≈ 4.4%，所以 10G 链路上 iperf3 测到 9.4~9.5 Gbps 左右就是**正常满速**，不是"没跑满"。巨帧（MTU 9000）时开销占比降到 1% 以下。
- 记住一个面试数字：**万兆线速 = 64 字节小包 148.8 Mpps**（千兆是 14.88 Mpps）——这是网卡/CPU 处理能力的经典标尺。

### 3.2 BDP（带宽延迟积）——理解"为什么打不满"的钥匙

```
BDP = 带宽 × RTT（往返延迟）
```

- 例：10G 链路 × 10ms RTT = 100 Mbit = **12.5 MB**；100G 链路 × 50ms RTT = 5 Gbit = **625 MB**。
- TCP 发送方同时最多只能有"一个窗口大小"的数据在途等待确认。**窗口 ≥ BDP 才能打满链路**。
- Linux 默认开启窗口自动缩放（window scaling），但自动调窗有上限（`net.ipv4.tcp_rmem` / `tcp_wmem` 的第三个值，常见默认 4~6MB）。**跨地域长肥链路（高速+高延迟）上，默认窗口经常不够 → 吞吐上不去**，解决办法见 §6.5。

### 3.3 TCP 为什么难打满：慢启动、丢包与 Mathis 公式

**慢启动**：TCP 连接建立后拥塞窗口从 10 个 MSS（Linux initcwnd=10）开始指数增长，每 RTT 翻一倍。高 RTT 链路上这个爬坡很慢——10 秒的默认测试可能有一半时间在爬坡，结果低估。对策：`-t` 加长 + `-O 2` 跳过前 2 秒统计。

**丢包对 TCP 的毁灭性影响——Mathis 公式**：

```
TCP 吞吐上限 ≈ MSS / (RTT × √p)     （p = 丢包率）
```

代入计算：MSS=1460B，RTT=100ms，丢包率 p=0.1%：

```
B = 1460×8 bit / (0.1s × √0.001) ≈ 11680 / 0.00316 ≈ 3.7 Mbps
```

**结论：100ms RTT 的链路上只要丢 0.1% 的包，TCP 吞吐理论上限就从"接近线速"塌到几 Mbps**。丢包率哪怕看似很小，对高速高延迟链路都是致命的。这是网络面试最经典的一道题。

### 3.4 拥塞控制算法

| 算法              | 特点                     | 适用           |
| --------------- | ---------------------- | ------------ |
| CUBIC（Linux 默认） | 基于丢包的拥塞检测，丢包即降速        | 同机房、低丢包网络    |
| BBR             | 基于带宽+时延测量，**对随机丢包不敏感** | 跨地域、有固有丢包的链路 |
| Reno            | 老算法，已被 CUBIC 取代        | 几乎不用         |

iperf3 可以按流指定：`iperf3 -C bbr -c server`。做一组"CUBIC vs BBR 同链路对比"实验是简历上很好写的一条。

### 3.5 多流（-P）的意义

`-P 4` = 同时开 4 条 TCP 连接并行传输。三条原因：

1. **单流受单核 CPU 限制**（§3.8）：iperf3 每条流是单线程，多流可以分散到多个核；
2. **单流丢包后恢复慢**：一条流因丢包降速，整体吞吐就掉；多流互相"顶上去"；
3. **对应网卡多队列**：多队列网卡靠 RSS 把不同流分到不同核/队列，流数太少时队列利用不均。

结论：**高速链路（25G 以上）单流测不满是正常现象，多流聚合才是链路真实能力**。

### 3.6 UDP 模式与抖动（jitter）

- TCP 自带拥塞控制，会**自动探测链路极限**，所以 TCP 测试不需要指定速率。
- UDP 没有拥塞控制，**不发指令就默认 1 Mbps 慢慢发**（`-b` 默认值 1M——新手最常见的坑：忘了 `-b` 测出来永远是 1Mbps）。必须用 `-b 10G` 指定发送速率，甚至可以设成超过线速来测交换机的丢包行为。
- UDP 测试关心的指标是**丢包率和抖动**：
  - **抖动（jitter）**：iperf3 按 RFC 3550（RTP）的定义计算——相邻两个包到达间隔差值的滑动平均：`J = J + (|D| - J)/16`。单位 ms。抖动大说明链路时延不稳定，对实时业务（音视频、金融行情）致命。
  - 丢包率：`Lost/Total Datagrams`。目标是 0%；长时间测试下出现少量丢包要追查（网卡 ring buffer 不足、交换机 buffer 溢出、链路误码）。
- UDP 报文长度 `-l` 默认 1460 字节（动态适配 MSS），**不要设得超过路径 MTU-28**，否则 IP 分片会让结果失真（分片后的丢包统计异常、CPU 开销暴涨）。

### 3.7 方向：正向 / 反向（-R）/ 双向（--bidir）

- 默认正向：客户端发送，服务端接收。测的是 client→server 方向。
- `-R` 反向：服务端发送，客户端接收。测 server→client 方向。
- `--bidir`（3.7+）：两个方向**同时**压满。测全双工能力。注意双向同时跑时两条流会互相影响（共享链路），结果要按 send/receive 两部分分别解读。

### 3.8 CPU 限制与网卡 offload

- **iperf3 每条流是单线程**。单流的极限取决于单核性能，通常 25~40 Gbps 左右就到顶（视 CPU 而定）。现象：吞吐卡在某个值，`top` 按 `1` 看到某核 100%。
- 对策：`-P 8` 多流分散到多核；`-A` 显式绑核；大吞吐测试时**服务端 CPU 同样要够**（接收侧也要处理报文）。
- **网卡 offload**：TSO/GSO（发送分段卸载）、GRO/LRO（接收聚合卸载）把大块数据的协议处理交给网卡，关掉后 CPU 压力暴涨、吞吐骤降。高速网测试的第一检查点：`ethtool -k eth0 | grep offload`。

## 5. 输出解读（★ 必练：逐列读懂）

### 5.1 TCP 测试输出

```
$ iperf3 -c 192.168.100.2 -t 10
Connecting to host 192.168.100.2, port 5201
[  5] local 192.168.100.1 port 54321 connected to 192.168.100.2 port 5201
[ ID] Interval           Transfer     Bitrate         Retr  Cwnd
[  5]   0.00-1.00   sec  2.90 GBytes  24.9 Gbits/sec    0   2.50 MBytes
[  5]   1.00-2.00   sec  2.90 GBytes  24.9 Gbits/sec    0   2.55 MBytes
[  5]   2.00-3.00   sec  2.90 GBytes  24.9 Gbits/sec    0   2.60 MBytes
...（每秒一行）
[ ID] Interval           Transfer     Bitrate         Retr
[  5]   0.00-10.00  sec  28.9 GBytes  24.9 Gbits/sec    0             sender
[  5]   0.00-10.04  sec  28.9 GBytes  24.8 Gbits/sec                  receiver

iperf Done.
```

逐列解读：

| 列            | 含义                  | 怎么用                                        |
| ------------ | ------------------- | ------------------------------------------ |
| `Interval`   | 该行统计的时间窗口           | 逐秒看稳定性                                     |
| `Transfer`   | 该窗口内传输的数据量          | 累计校验                                       |
| `Bitrate`    | 该窗口平均速率             | **核心指标**                                   |
| `Retr`       | **TCP 重传的段数**       | **0 = 链路健康**。持续 >0 说明有丢包/拥塞，吞吐会抖动，需要排查（§8） |
| `Cwnd`       | 发送方拥塞窗口大小（TCP 内部状态） | 观察拥塞控制是否在收缩窗口；长时间被压得很小 = 持续丢包              |
| `sender` 行   | 发送端统计               | **对外报告取 sender 行**（吞吐由发送方决定）               |
| `receiver` 行 | 接收端统计               | 时间略长（+0.04s，尾部数据排空），速率略低属正常                |

**关键结论**：`Retr=0` 且逐秒 Bitrate 稳定 = 链路干净、结果可信。只要 Retr 持续非零，先解决丢包再谈吞吐数字。

### 5.2 UDP 测试输出

```
$ iperf3 -c 192.168.100.2 -u -b 10G -t 10
[ ID] Interval           Transfer     Bitrate         Jitter    Lost/Total Datagrams
[  5]   0.00-1.00   sec  1.19 GBytes  10.2 Gbits/sec  0.015 ms  0/870123 (0%)
[  5]   1.00-2.00   sec  1.19 GBytes  10.2 Gbits/sec  0.014 ms  0/870124 (0%)
...
[  5]   0.00-10.00  sec  11.9 GBytes  10.2 Gbits/sec  0.015 ms  12/8701230 (0.00014%)  sender
[  5]   0.00-10.00  sec  11.9 GBytes  10.2 Gbits/sec  0.015 ms  12/8701230 (0.00014%)  receiver
```

- `Jitter`：抖动（ms），定义见 §3.6。局域网内应 < 0.1ms，跨地域通常 < 1ms。抖动大 → 排查链路拥塞、CPU 中断不均。
- `Lost/Total Datagrams`：丢包数/总包数。**目标 0%**。UDP 不重传，丢 1 个就是 1 个，业务侧（视频/语音）会直接受损。
- 注意 Bitrate 略高于 `-b` 设定值（10.2G vs 10G）：UDP 是恒定速率发送，实际值包含协议开销、且 iperf3 按时间窗计算，属正常。

## 6. 典型场景模板（可直接运行）

### 6.1 基础 TCP 测试

```bash
# 服务端（目标机器上）
iperf3 -s

# 客户端：默认 10 秒单流
iperf3 -c 192.168.100.2

# 更规范：60 秒、逐秒报告、跳过前 2 秒慢启动
iperf3 -c 192.168.100.2 -t 60 -i 1 -O 2
```

### 6.2 多流 / 反向 / 双向

```bash
iperf3 -c 192.168.100.2 -P 4          # 4 条并行流（打满 25G+ 链路的常规手段）
iperf3 -c 192.168.100.2 -P 8 -t 60    # 8 流长测
iperf3 -c 192.168.100.2 -R            # 反向：测服务端→客户端方向
iperf3 -c 192.168.100.2 --bidir -P 4  # 双向并发，各 4 条流（测全双工）
```

### 6.3 UDP 丢包/抖动测试

```bash
# 以 10G 速率打 60 秒，看丢包与抖动
iperf3 -c 192.168.100.2 -u -b 10G -t 60 -i 1

# 超线速打流（测交换机 buffer/丢包行为）：10G 链路打 15G
iperf3 -c 192.168.100.2 -u -b 15G -t 30

# 语音类负载：小包、低速率
iperf3 -c 192.168.100.2 -u -b 1M -l 160 -t 60
```

### 6.4 高速链路（25G/100G）完整调优清单

按顺序检查执行：

```bash
# ① 确认端口协商速率与双工
ethtool eth0 | grep -E "Speed|Duplex"

# ② 确认 offload 开启（TSO/GSO/GRO 必须 on）
ethtool -k eth0 | grep -E "tcp-segmentation|generic-segmentation|generic-receive"

# ③ 巨帧：MTU 9000 必须端到端一致（两端主机 + 沿途交换机）
ip link set eth0 mtu 9000

# ④ 多队列与中断分布（-P 流数 ≤ 队列数才有意义）
ethtool -l eth0

# ⑤ 大窗口（配合 -O 跳过慢启动）
iperf3 -c 192.168.100.2 -P 8 -w 64M -t 60 -O 2 -i 1

# ⑥ CPU 绑核（跨 NUMA 要绑在同一 NUMA 节点上）
iperf3 -c 192.168.100.2 -P 8 -A 2,3,4,5,6,7,8,9

# ⑦ 巨帧生效校验（MSS = MTU - 40 = 8960）
iperf3 -c 192.168.100.2 --set-mss 8960 -t 60
```

### 6.5 大 BDP 长肥链路（跨地域/专线）

```bash
# 计算 BDP 再设窗口：如 1G 带宽 × 80ms RTT = 80Mbit = 10MB
# iperf3 侧：socket 缓冲区至少 2×BDP
iperf3 -c remote.example.com -w 20M -t 120 -O 5 -i 1

# 系统侧：抬高自动调窗上限（两端都要设）
sysctl -w net.ipv4.tcp_rmem='4096 87380 134217728'
sysctl -w net.ipv4.tcp_wmem='4096 65536 134217728'
sysctl -w net.core.rmem_max=134217728
sysctl -w net.core.wmem_max=134217728
```

### 6.6 拥塞控制对比实验（简历好素材）

```bash
# 同一链路分别测，对比吞吐与 Retr
iperf3 -c 192.168.100.2 -C cubic -t 60 -i 10 -T cubic
iperf3 -c 192.168.100.2 -C bbr   -t 60 -i 10 -T bbr
# 全局切换（需 root）
sysctl -w net.ipv4.tcp_congestion_control=bbr
```

### 6.7 BF2 / DPU 场景（结合你的实验）

- **host ↔ DPU 网络**：服务端跑在 BF2 的 Ubuntu 上（`iperf3 -s`），主机端打流，测管理口（oob）与数据口两个网络——两者的带宽预期完全不同，对比结果本身就是有价值的实验数据。
- **双向**：DPU 场景常见"主机到 DPU 上行 + DPU 到主机下行"同时发生，用 `--bidir` 测全双工。
- **注意区分**：iperf3 走 TCP/IP 协议栈，测的是 IP 网络吞吐；**RDMA/RoCE 流量 iperf3 测不了**（绕过内核协议栈），要用 perftest 工具集（`ib_send_bw` / `ib_write_bw`）。这条区分在面试 DPU 相关岗位时非常加分。
- **与计数器采集配合**：同 fio 一样，iperf3 可以作为确定性网络负载发生器——固定 `-P`、`-b`（UDP 恒定速率），同时跑你们的 PMC 计数器采集，负载强度就是可控变量。

## 7. 高级用法

### 7.1 JSON 输出 + jq 自动化

```bash
iperf3 -c 192.168.100.2 -t 60 -P 4 -J > result.json

# 提取关键指标
jq '{bits_per_sec: .end.sum_sent.bits_per_second,
```

JSON 化之后可以写脚本批量测多组参数（不同 `-P`、不同窗口、不同拥塞算法）自动生成对比表——这就是简历上的"自动化网络性能测试"。

### 7.2 服务端管理与多测试标记



## 8. 测试方法论与常见陷阱（★ 排查能力是面试分水岭）

1. **单核 CPU 瓶颈**：吞吐卡在 25~40G 不动、`top` 按 `1` 看到单核 100% → 这是 iperf3 单线程的固有特性，不是链路问题。对策：`-P` 多流、`-A` 绑核、`-Z` zerocopy。
2. **UDP 忘 `-b`**：默认 1Mbps，测出来永远 1M。看到 UDP 结果异常偏低先查这个。
3. **慢启动低估结果**：默认 10 秒测试里爬坡占比大，高速高 RTT 链路尤其明显。规范做法：`-t ≥ 30`、`-O 2` 跳过。
4. **巨帧 MTU 不一致**：一端 9000 一端 1500 → 分片/丢包/性能异常。巨帧必须端到端一致（主机、交换机、对端），改完用 `ping -M do -s 8972` 验证路径。
5. **offload 被关闭**：TSO/GSO/GRO 关了之后高速网吞吐骤降、CPU 飙升。`ethtool -k` 是第一检查点。
6. **流数与网卡队列不匹配**：多队列网卡（4/8/16 队列）上单流只会命中一个队列 → 单流测不满是设计使然。看 `/proc/interrupts` 的中断分布。
7. **NUMA 跨节点**：网卡 PCIe 挂在 NUMA 0，进程跑在 NUMA 1 → 跨节点内存访问拖慢吞吐。用 `numactl` / `-A` 绑同一节点核。
8. **结果波动与"最好值"**：网络测试受环境影响大，规范做法是**跑 3 次取最好值或中位数**，并记录环境（时段、链路负载、两端版本）。报告单次结果没有意义。
9. **单位混淆**：`10G = 1.25 GB/s`。Bitrate 默认显示 Gbits/sec，`-f M` 可以换成 MBytes。面试/汇报时先说清单位。
10. **Retr 非零但吞吐还行**：轻微重传不代表链路废了，但要追查来源：`netstat -s | grep retrans`、`sar -n EDEV`、抓包 `tcpdump` 看是否真丢包还是超时重传。
11. **端口被拦**：5201 被防火墙/安全组挡了 → 连接超时。自定义端口用 `-p`（服务端和客户端同设）。
12. **Windows 客户端偏低**：Windows 网络栈默认行为（窗口、offload 差异）可能让结果低于 Linux 客户端，对比实验要同 OS。
13. **同时双向测试的解读**：`--bidir` 两方向同时压会互相影响，send/receive 都低于各自的单向值属正常，报告时要说明。
14. **安全**：iperf3 **无加密无认证**，只应在内网/受控环境使用，不要长期在公网暴露服务端。

## 9. 简历与面试（★ 自测）

### 简历写法参考

> **网络性能测试**：熟练使用 iperf3 进行 TCP/UDP 吞吐、丢包率与抖动测试；完成 25G/100G 链路验收，通过多流并发（-P）、窗口调优（BDP）、CPU 绑核与网卡 offload 检查定位并解决单流吞吐瓶颈；输出 JSON 报告并用 jq 实现批量测试自动化。

### 高频面试题与参考答案

**Q1：iperf3 TCP 输出里的 Retr 列是什么？非零说明什么？**
答：Retr 是 TCP 重传的段数。持续非零说明有丢包或超时重传，链路存在质量问题；重传会触发拥塞控制收缩窗口（看 Cwnd 列），吞吐随之抖动或下降。Retr=0 且逐秒速率平稳才是干净的结果。

**Q2：100G 链路单流只测到 30 多 G，怎么排查？**
答：按顺序：① 确认不是 CPU 瓶颈——iperf3 单流是单线程，`top` 看单核是否 100%，是则 `-P 8` 多流分散；② 查窗口是否够 BDP（100G × RTT），不够则 `-w` 加大；③ `ethtool -k` 查 offload；④ 查 MTU/巨帧一致性；⑤ 查网卡队列数与流数匹配；⑥ 绑核消除 NUMA 影响。多流聚合能打满，说明是单流协议/CPU 限制而非链路损坏。

**Q3：BDP 是什么？怎么算？窗口怎么设？**
答：BDP = 带宽 × RTT，是"在途数据不中断发送"所需的最小窗口。如 10G × 10ms = 12.5MB。iperf3 用 `-w` 设 socket 缓冲区，系统层调 `tcp_rmem/tcp_wmem` 上限。窗口 < BDP 时链路空转、吞吐受限。

**Q4：TCP 只丢 0.1% 的包，为什么吞吐可能掉一半以上？**
答：Mathis 公式 `B ≈ MSS/(RTT·√p)`：100ms RTT 上 0.1% 丢包时理论吞吐上限只有几 Mbps。CUBIC 把丢包当拥塞信号，一丢包就大幅收缩窗口；BBR 基于时延探测、对随机丢包不敏感，长肥链路建议用 BBR。

**Q5：iperf3 的 jitter 是怎么定义的？**
答：按 RFC 3550（RTP）定义：相邻包到达时间差与历史抖动值的滑动平均（`J = J + (|D| - J)/16`），反映时延的短期波动，对实时业务很重要。

**Q6：TCP 测试不指定速率也能测到极限，UDP 为什么必须 `-b`？**
答：TCP 自带拥塞控制，会自动加窗探测链路极限；UDP 无任何反馈控制，不指定就按默认 1Mbps 发，必须用 `-b` 设定发送速率，甚至超线速打流来观测丢包行为。

**Q7：sender 和 receiver 两行结果为什么略有差异？取哪个？**
答：receiver 行时间略长（尾部数据排空）、速率略低，属正常。吞吐由发送方决定，报告取 sender 行；receiver 行用于核对实际收到多少。

**Q8：怎么设计一次完整的链路验收测试？**
答：① 确认端口协商速率/双工与 MTU 一致性；② 单流 TCP 基线（30~60s，-O 跳过慢启动）；③ 多流（-P 8）聚合验证链路真实容量；④ 双向 `--bidir` 测全双工；⑤ UDP `-b` 满速测丢包与抖动；⑥ 超速打流测交换机缓冲行为；⑦ 多次取最好值并记录环境，输出 JSON 报告。
